Plugin documentation

Readback

Your agent reads back what it just did, in two or three spoken sentences, at the end of every reply. The reply itself does not change. Nothing listens to you.

What it does, and what it is not

You work exactly as you do now. You type, or you dictate with your editor's own dictation. The agent answers in full, with its tables, its code and its detail.

On top of that, a voice tells you the outcome: what happened and what comes next, in a couple of sentences. You can act on it without reading the whole reply first, and read the detail only when you need it.

This is not a voice conversation

There is no microphone, no wake word, no listening loop, no push-to-talk. Readback is output only. Nothing is ever recorded, and no permission dialog is ever raised.

How the spoken line is produced

The agent writes it itself, as the last line of its reply, marked with a speaker emoji in a quote block: 

> 🔊 Fixed the token expiry check in the middleware, it used
>    less-than instead of less-or-equal. Run the type check
>    before you push.

That line is visible in your terminal too, so it doubles as a summary you can read. The plugin lifts it out, cleans the markdown, and sends it to a speech engine.

This matters for two reasons. It costs nothing extra: no second model, no extra latency, no per-turn charge. And the summary is written by the model that did the work, with full context, rather than by something guessing from the outside.

The turn cycle

Two hooks, one at each end of the turn.

you send a message │ ▼ UserPromptSubmit hook │ is there a sentinel file for this session? ├── no ──▶ prints nothing. Session behaves exactly as always. └── yes ─▶ injects the instruction to close with a 🔊 line │ ▼ the agent answers normally, ending with that line │ ▼ Stop hook │ reads last_assistant_message straight from its own payload │ extracts the 🔊 line, applies the pronunciation map │ ├── nothing marked ──▶ silence, exit 0 │ ▼ POST to the speech engine ──▶ audio plays in the background

The Stop hook returns control in under half a second. Generating and playing the audio happen detached, so your session is never blocked waiting for a voice.

It fails silent, always

Readback is off, no line was marked, the speech engine is down, the provider returns an error, no audio player exists: every one of those paths exits quietly with status 0. A voice problem can never interrupt your work or fail your turn.

Multiple sessions at once

This is the part worth reading carefully if you run several agents in parallel, one per worktree or one per task.

Each session decides on its own

The switch is a file named after the session id, inside the plugin's data directory. Turning readback on in one session creates that session's file and touches nothing else. 

<data dir>/sessions/
├── d80a037b-17c3-…    ← this one speaks
└── 4f21ba9c-88de-…    ← and this one
                       every other session: silent

The hooks still fire in every session, because they are installed globally. In a session with no sentinel they find nothing and exit immediately. That costs a few milliseconds and produces no output, no context, no sound.

So can more than one session speak? Yes

There is no limit, and no notion of one session "holding" the voice. Turn it on in three sessions and all three will speak.

They queue, they do not overlap

Two sessions finishing at the same moment would talk over each other, which is unusable. A lock in the data directory prevents it: the second one waits for the first to finish, then plays. You hear both, one after the other, complete.

A lock older than five minutes is treated as dead and reclaimed, so a crashed session can never leave the voice stuck for the others.

SituationWhat happens
One session on, three offOnly that one speaks. The others never touch audio.
Three sessions on, finishing apartEach speaks when its turn ends. Normal.
Three sessions on, finishing togetherThey queue. You hear all three in sequence, none cut off.
A speaking session crashesIts lock expires after five minutes and the rest carry on.
A subagent finishes inside a sessionNothing is spoken. Only the main agent's message is ever read.

Practical advice

Turning it on in every parallel session is technically fine and acoustically exhausting: several voices in a row, and you cannot tell which agent is talking. Turn it on in the session you are actually watching. Leave the background workers silent and read their output when you get to them.

The list action shows every session currently speaking, which is how you find one you forgot about.

Install

  1. Add the marketplace and install the plugin Once per machine.
  2. Get a speech engine running The plugin ships no model and downloads nothing. Without an engine it stays silent.
  3. Turn it on where you want it Per session. It takes effect on your next message. 
# 1
/plugin marketplace add upex-galaxy/agentic-user-skills
/plugin install readback@upex-agentic

# 2 — a local engine, about two minutes
uvx voice-mode-install --yes
voicemode service install kokoro

# 3
/readback:speak on

Step 2 installs VoiceMode, which runs Kokoro as a background service. You do not need the rest of VoiceMode, and you are not obliged to use it at all: any OpenAI-compatible /v1/audio/speech server works. Point KOKORO_URL at yours in /plugin → readback → Configure.

Verify everything with /readback:speak doctor, which reports the engine, the audio player, and where your files live.

Selecting ElevenLabs never risks silence: if the key is missing, the request fails, or the response is not audio, readback falls back to Kokoro automatically and says nothing about it. The failed response is saved in the data directory if you want to look.

Kokoro voices are per language, with the language in the id: af_ and am_ for English, ef_ and em_ for Spanish, and so on. The default is af_heart. If your agent answers you in Spanish, set ef_dora or the voice will read Spanish with an English accent.

Pronunciation

Small speech models mangle technical terms embedded in another language. "Supabase" comes out as a native word, "n8n" as noise. This is not a voice quality problem, it is a letters-to-sounds problem, and paying for a better engine does not reliably fix it.

So the text is rewritten before it reaches the engine. The rules are plain text, applied on word boundaries, case-insensitive, longest pattern first: 

middleware      mídelwer
Supabase        Supabéis
n8n             ene ocho ene

Nothing on your screen changes. It is a layer between the text and the speaker, so it works the same with any provider.

The plugin ships 50 rules, tuned for Spanish speech reading English technical terms. Add your own in a pronunciation.txt inside the data directory (doctor prints the exact path). Yours are applied last, win on conflict, and survive plugin updates.

When it does not speak

Start with /readback:speak doctor. It answers most of this in one screen.

SymptomLikely causeFix
Nothing at all, ever No speech engine answering doctor will say NOT READY. Install Kokoro, or fix KOKORO_URL.
Silent right after turning it on Working as designed It starts on your next message, not the one that enabled it.
Speaks sometimes, not always The agent skipped the marked line Expected on trivial turns. If it happens constantly, the reminder is not reaching the model: check that the plugin is enabled.
Technical terms sound wrong Missing pronunciation rules Add them to your own pronunciation.txt. doctor prints the path.
Wrong accent for the language Voice belongs to another language Kokoro voice ids carry the language as a prefix. Pick one that matches.
You hear everything twice A second installation is also hooked An older manual setup in settings.json alongside the plugin. Remove one.
Voices overlap Should not happen The lock serialises playback. If it persists, delete the stale lock directory shown by doctor.
Stops after many turns The engine recycled itself Some Kokoro setups terminate after a fixed number of requests and take ~15s to come back. Raise that limit in the service config.

Privacy

No microphone is ever opened. Nothing you say or type is recorded, and no audio is kept: the generated file is deleted right after it plays.

The only text that leaves the process is the spoken line itself, and with the default provider it travels to 127.0.0.1 — your own machine. Choosing ElevenLabs sends that one line to their API instead. Everything else is identical.

Your session ids appear as filenames in the data directory, and nothing else is stored there beyond your own pronunciation rules.
